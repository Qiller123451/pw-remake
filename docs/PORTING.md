# Porting the browser remake to C#

The C# code is a port of the ParaWorld Toolkit's browser remake (`remake/src`, JavaScript, ~1.9 MB) - commit
`98c7703` of <https://github.com/Qiller123451/pw-exporter>. Its rules were ported from the original scripts with
line references (`remake/docs/spec/*.md`); keeping the port close to the JS keeps those references valid and makes
bugs comparable. This file says how to port and what is done.

## Conventions

* **One JS module → one C# file** of the same name in PascalCase (`systems/combat.js` → `src/Sim/Systems/Combat.cs`),
  with the module's header comment kept (it says which original script it follows) and a line
  `// Ported from remake/src/game/systems/combat.js (pw-exporter 98c7703).`
* **World systems are partial classes.** The JS mixes the systems into `World.prototype`; in C# every system file is
  `public partial class World` in namespace `PwRemake.Sim.World`, so `this` is the world in both.
* **Names**: functions and fields PascalCase (`takeDmg` → `TakeDmg`, `u.hp` → `u.Hp`), constants as in the JS
  (`WILD_CAP` → `WildCap`). Keep the JS names otherwise - a reader with the JS beside must find things.
* **Loose JS objects become classes.** A unit's `task` (`{type: 'gather', node, phase}`) is a `UnitTask` class with
  the fields any task uses; `e.st` (status) is a `Status` class. Prefer fields over dictionaries. Where the JS
  really keys by string (tech tree paths, trigger parameters, the AI's tables), C# does too.
* **Numbers**: `double` (as JS). `Math.random()` → `W.Rng.Next()`; never `System.Random`. `Math.sin / cos / tan /
  atan / atan2 / asin / acos / exp / log / pow` → `SMath.Sin` ... (FdLibm.cs: the same bits on every machine, and the
  same as V8's - docs/MULTIPLAYER.md "Determinism"); parsing and formatting with the invariant culture.
* **No engine in src/Sim.** What the JS simulation asked of three.js (a model's link positions, animation lengths,
  footprints) comes from the asset manifest (`assets/manifest.json`), read by `Content` - the same data the JS
  had through the manifest. Drawing code goes to `game/src/View`.
* **Events**: `world.emit('built', {e})` → `W.Emit(...)` (World.Events, read by the view and the interface once per
  frame). Never call the view from the simulation.
* **Delayed things are data**: `world.later(sec, kind, args)` and periodic effects name a handler (`Delayed.cs`);
  no lambdas stored in the world state (saved games need it, as in the JS since 2026-10-11).
* **The view never changes the world.** Everything that changes it is a command (also a scene's end, a debug tool);
  what the world asks of the interface goes through `IMissionPresenter` (recorded for saved games: docs/SAVES.md).
  The JS's view moved cutscene actors, kept the fog of war and drained the events at frames - not here.
* **Logging**: `static readonly Logger L = Log.For("Systems.Combat");` Use Debug/Trace for what helps to follow a
  bug, Warn for data problems (once: `L.WarnOnce(key, msg)`), Error with the exception for failures. A failing
  trigger action, AI module or system tick logs and goes on; it does not stop the game.
* **Comments** in the style of the JS: what a rule is and where it comes from (`// FightingObj.usl:5628`), not
  what the next line does.
